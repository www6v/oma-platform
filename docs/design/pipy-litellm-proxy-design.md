# Design: piPy + LiteLLM Proxy（多 API key 负载均衡）

Generated by /plan-eng-review on 2026-07-18
Branch: master
Repo: oma monorepo (oma-platform)
Status: APPROVED (design only, implementation deferred)
Mode: Builder

## TL;DR

在 docker-compose 里加一个 LiteLLM proxy 容器，piPy 把 LLM 请求发给 LiteLLM（而不是直接发给 Anthropic），LiteLLM 在多个 API key 之间做负载均衡和 fallback。**本次只写设计文档，不实现**。

## Problem Statement

piPy (oma-harness) 当前只支持单个 `ANTHROPIC_API_KEY`。用户流量上升时，单 key 命中 Anthropic 的 RPM/TPM 速率限制，导致请求失败或排队。

**目标**：通过多个 API key 分摊请求，提升整体吞吐，绕过单 key 限制。

**非目标**：
- 解决 piPy 的 CPU 并发问题（那是阶段 2）
- 共享多个 piPy 实例间的状态（阶段 2）

## 关键决策

| # | 决策 | 选项 | 理由 |
|---|------|------|------|
| 1 | 架构模式 | **LiteLLM proxy** (不是 2 个 piPy) | 不用改 harness 代码；多 key 负载均衡是 LiteLLM 的专长；避免 2 piPy 带来的 SQLite 分片问题 |
| 2 | 范围 | **Phase 1 先做 LiteLLM** | 先解决眼前问题，Phase 2 按需加码 |
| 3 | LLM 后端 | **Anthropic 官方 API** | KV cache 由 Anthropic 管理，不需要 sticky session |
| 4 | LiteLLM 版本 | **固定版本**（如 `v1.75.0`） | 可重复构建、升级是明确操作、易回滚 |
| 5 | 429 fallback | **立即切下一个 key** | 用户体验优先，LiteLLM 默认行为 |
| 6 | API key 命名 | **显式命名**（`ANTHROPIC_API_KEY_1`, `_2`, ...） | 与 LiteLLM yaml 结构一一对应，可读性好 |
| 7 | Pre-flight | **必须先做兼容性验证** | 30 分钟验证避免几小时调试 |

## Architecture (Phase 1)

```
┌──────────────┐     ┌──────────────────┐     ┌─────────────────┐
│  用户请求     │──► │  oma-platform    │──► │  oma-harness    │
│  (Console)   │     │  (Go, 8787)      │     │  (piPy, 8090)   │
└──────────────┘     └──────────────────┘     └────────┬────────┘
                                                       │
                                                       │ ANTHROPIC_BASE_URL
                                                       │ = http://litellm:4000
                                                       ▼
                                              ┌──────────────────┐
                                              │  LiteLLM Proxy   │
                                              │  (port 4000)     │
                                              │  - key1 (main)   │
                                              │  - key2 (fallback)│
                                              │  - key3 (future) │
                                              └────────┬─────────┘
                                                       │
                                      ┌────────────────┼────────────────┐
                                      ▼                ▼                ▼
                               Anthropic API    Anthropic API    Anthropic API
                               (key1 生效)      (key2 生效)      (key3 生效)
```

## Architecture (Phase 2 — multi-piPy)

Same-host multi-piPy behind external Nginx (session sticky) is documented in
[`docs/HARNESS_LOAD_BALANCING.md`](../HARNESS_LOAD_BALANCING.md). Go still uses
a single `HARNESS_URL` pointing at the LB; affinity uses `X-OMA-Session-ID`.
MySQL is required for multi-replica; remote hosts remain cold standby (no NFS).

```
                         ┌──────────────────┐
                         │  Nginx (LB)      │
                         │  hash session id │
                         └────────┬─────────┘
                    ┌─────────────┼─────────────┐
                    ▼             ▼             ▼
             ┌─────────┐   ┌─────────┐   ┌─────────┐
             │ piPy-1  │   │ piPy-2  │   │ piPy-N  │
             │ (MySQL) │   │ (MySQL) │   │ (MySQL) │
             └────┬────┘   └────┬────┘   └────┬────┘
                  └─────────────┼─────────────┘
                                ▼
                         ┌──────────────────┐
                         │  LiteLLM Proxy   │
                         │  (per virtual key)│
                         └──────────────────┘
```

## Scope (本次实现)

### In scope

1. 新增 `deploy/Dockerfile.litellm`（或直接引用官方固定版本镜像）
2. 新增 `deploy/litellm_config.yaml`（多 key 配置 + 路由策略）
3. 修改 `deploy/docker-compose.yml`：加入 `litellm` 服务 + 健康检查
4. 修改 `oma-platform/.env`：
   - `ANTHROPIC_BASE_URL=http://litellm:4000`
   - `ANTHROPIC_API_KEY_1=sk-ant-...`
   - `ANTHROPIC_API_KEY_2=sk-ant-...`
5. 修改 `oma-platform/.env.example`：同上（不带实际值）
6. 新增 `docs/LITELLM_SETUP.md`：说明 key 配置流程
7. Pre-flight 验证脚本：`scripts/verify_litellm_anthropic_compat.sh`
8. E2E 测试：验证端到端 LLM 调用 + key 轮询 + fallback

### Not in scope (明确推迟)

- **MySQL 迁移**：Phase 2 才需要（当拆多个 piPy 时）
- **Nginx LB**：Phase 2 才需要（当 piPy CPU 成瓶颈时）
- **多 piPy 实例**：Phase 2 才需要
- **LiteLLM 可观测性接入**：见 TODO
- **CN 镜像镜像化**：见 TODO
- **API key 热更新**（不重启 LiteLLM 加 key）：未来考虑，先接受重启
- **Secret 管理升级**（Vault / Docker secrets）：先 .env，后续升级

## TODO (记录在案，未来做)

### TODO-1: CN 镜像镜像化 LiteLLM

**What:** 写一个脚本，定期把 LiteLLM 官方镜像拉到阿里云 ACR（或其他 CN 可达 registry）。

**Why:** `ghcr.io` 在 CN 经常拉不动。生产部署时拉取超时导致 `docker-compose up` 失败。

**Pros:** 部署稳定快速；不受 GitHub 访问影响。

**Cons:** 需要维护镜像脚本（10 分钟写好，偶尔检查更新）。

**Context:** 现有 oma-platform 已经在用 CN 镜像（mirrors.aliyun.com for apt, pypi.tuna.tsinghua.edu.cn for pip）。LiteLLM 镜像也要同样处理。

**Depends on / blocked by:** 无

### TODO-2: LiteLLM 可观测性接入

**What:** 接入 Langfuse 或 Datadog。LiteLLM 内建支持 Langfuse（设 `LANGFUSE_PUBLIC_KEY`, `LANGFUSE_SECRET_KEY`, `LANGFUSE_HOST` env vars 即可）。

**Why:** 没有可观测性，调试 key 轮询问题只能看 stdout 日志。接入后有 dashboard 看每个 key 的调用量、延迟、成本、失败率。

**Pros:** 成本可见（每个 key 花了多少钱）；问题定位快（哪个 key 经常 429）。

**Cons:** 多 30 分钟配置；多一个服务依赖（Langfuse 自托管或用 SaaS）。

**Context:** LiteLLM 的 Langfuse 集成是生产级成熟的。Langfuse 自托管也简单（一个 docker-compose）。

**Depends on / blocked by:** 无

### TODO-3: API key 使用指标

**What:** 暴露 Prometheus 指标或接入 LiteLLM 的内建 metrics 端点，监控每个 key 的使用量、成本、延迟。

**Why:** 即使不接入 Langfuse，也应该有基本指标。避免某个 key 成本失控才发现。

**Pros:** 主动发现问题；成本可控。

**Cons:** 多一个 metrics 系统要维护。

**Context:** LiteLLM 内建有 `/metrics` 端点（Prometheus 格式）。可以接入现有 Prometheus/Grafana（如果有）。

**Depends on / blocked by:** 无

### TODO-4: API key 热更新

**What:** 不重启 LiteLLM 就能加/减 key。

**Why:** 当前每加一个 key 要重启 LiteLLM 容器。如果 key 频繁变化（比如按天轮换），重启成本高。

**Pros:** 运维更灵活。

**Cons:** 需要用到 LiteLLM 的 DB-backed config（Postgres）或 Enterprise 特性。

**Context:** LiteLLM 的 DB-backed config 允许通过 API 动态修改 model_list。但要额外部署 Postgres 给 LiteLLM 用。

**Depends on / blocked by:** 无

## Failure modes

| 失败场景 | 严重度 | 是否有测试覆盖 | 是否有错误处理 | 用户是否看到清晰错误 |
|---------|--------|--------------|--------------|------------------|
| LiteLLM 容器挂 | 高 | ❌ | ⚠️ piPy 收到 connection refused | ⚠️ 可能显示 500 不清晰 |
| 所有 key 同时 429 | 中 | ❌ | ✅ LiteLLM 抛 rate limit error | ❓ 看 piPy 怎么处理 |
| 某个 key 配置错（格式错） | 中 | ❌ | ✅ LiteLLM 启动时验证失败 | ✅ 容器起不来，日志清晰 |
| 某个 key 被 Anthropic 封禁 | 中 | ❌ | ✅ LiteLLM fallback 到其他 key | ✅ 用户无感知 |
| LiteLLM 配置 yaml 语法错 | 低 | ❌ | ✅ 容器启动失败 | ✅ 日志清晰 |
| piPy 与 LiteLLM 不兼容 | 高 | ❌ (pre-flight) | ❌ | ❌ 调用失败，原因不清 |
| CN 拉取 LiteLLM 镜像超时 | 中 | ❌ | ❌ | ✅ docker-compose 报错 |
| 单个 LLM 请求超时 | 低 | ❌ | ✅ LiteLLM 默认 10 分钟超时 | ⚠️ 看 piPy 超时处理 |

**Critical gaps (无测试 + 无错误处理 + 静默失败):**
- LiteLLM 容器挂时，piPy 怎么报错给用户？
- Anthropic SDK + LiteLLM 兼容性问题（pre-flight 验证覆盖）

## 风险矩阵

| 风险 | 严重度 | 概率 | 缓解 |
|------|--------|------|------|
| LiteLLM 单点故障 | 高 | 低 | LiteLLM 进程轻量、重启快；Phase 2 可加副本 |
| 多一层网络延迟 | 低 | 高 | 同 docker network，延迟 < 1ms |
| LiteLLM 配置错 | 中 | 中 | 健康检查 + 启动时验证 key 格式 |
| CN 镜像拉取慢 | 中 | 高 | 提前镜像（TODO-1） |
| Anthropic SDK 不兼容 | 高 | 低 | Pre-flight 验证（T0）|
| 成本失控（某个 key 用太多） | 中 | 中 | TODO-2 Langfuse 监控 |

## Worktree parallelization strategy

实现阶段的工作可以并行：

| Step | Modules touched | Depends on |
|------|----------------|------------|
| T0 (Pre-flight) | scripts/ | — |
| T1 (LiteLLM config) | deploy/ | — |
| T2 (docker-compose) | deploy/ | T1 |
| T3 (.env) | (root) | — |
| T4 (docs) | docs/ | — |
| T5 (E2E test) | test/ | T0, T1, T2, T3 |
| T6 (regression test) | harness/tests/ | T2, T3 |

**Parallel lanes:**
- **Lane A (配置):** T1 → T2 → T5/T6 (sequential, 都在 deploy/)
- **Lane B (脚本):** T0 (independent, scripts/)
- **Lane C (env/docs):** T3, T4 (independent)

**Execution order:**
1. 启动 Lane A + B + C 并行（3 个 worktree）
2. Lane A 完成 T1/T2 后，T5/T6 需要等 Lane B (T0) 和 Lane C (T3) 完成
3. 合并三个 worktree

**Conflict flags:** 无共享模块冲突（deploy/ 归 Lane A，scripts/ 归 Lane B，docs/ 归 Lane C）。
